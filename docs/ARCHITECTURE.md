# Архитектура Этапов 1–8

Документ описывает реализацию требований `PROJECT.md`, не заменяя спецификацию.

## Слои

- `app/` собирает layout и страницы; `App.tsx` не содержит бизнес-логики.
- `features/habits/` содержит общие `DayHabits` / `useDayHabits` для «Сегодня» и календаря;
  компоненты трекеров из `features/today/` отображают состояние и передают действия в hook.
- Hooks управляют подписками, состояниями загрузки/ошибок и сменой локального дня.
- `services/habit-service.ts` читает привычки, атомарно сохраняет отметки и добавляет количества.
- `services/duration-service.ts` проверяет ввод времени, сохраняет минуты и вычисляет оценки.
- `services/duration-statistics-service.ts` вычисляет последние 7 календарных дней из записей.
- `services/calendar-service.ts` читает видимый диапазон месяца и вычисляет заполненность дней.
- `services/streak-service.ts` вычисляет серии boolean-привычек и долю успехов до выбранной даты.
- `services/habit-note-service.ts` сохраняет заметки внутри существующих `HabitEntry`.
- `features/tasks/` содержит страницу задач, формы, карточку и общий дневной блок.
- `services/task-service.ts` проверяет задачи, выполняет CRUD и вычисляет порядок/просроченность.
- `features/goals/` содержит список и подробности целей, формы и подписки.
- `services/goal-service.ts` управляет целями, этапами и связями с существующими задачами.
- `features/statistics/` содержит выбор периода, сводку, карточки, графики и подписку `useStatistics`.
- `features/settings/` содержит настройки Habit, архив, file picker, preview и подтверждение восстановления.
- `services/habit-settings-service.ts` меняет только определения привычек и `archivedAt`.
- `services/backup-service.ts` читает и восстанавливает согласованный snapshot всех пяти таблиц;
  `backup-validation.ts` проверяет неизвестные входные данные до записи.
- `services/statistics/` получает общий снимок данных и рассчитывает показатели привычек,
  задач и целей; React-компоненты форматируют и отображают готовые результаты.
- `db/` содержит Dexie, версионированную схему и seed.
- `models/` содержит discriminated unions для универсальных сущностей.
- `lib/local-date.ts` отвечает за проверку и форматирование календарной даты.

## Habit и HabitEntry

`Habit` имеет общий ID, название, описание, порядок, временные метки и `archivedAt`.
Типы: `boolean`, `amount`, `duration`, `rating`. У `amount` есть цель и единица
измерения; у `duration` единица — минуты и есть массив `ratingRanges`.
Ввод реализован для `boolean`, `amount` и `duration`; отдельный тип `rating`
зарезервирован для будущего использования.

`HabitEntry` содержит `habitId`, локальную дату, тип и временные метки.
Boolean-запись хранит ровно одно состояние: `success`, `failure`, `no-data`.
Amount-запись хранит фактическое числовое `value`. Статус и процент не дублируются
в БД: сервис вычисляет `success` при `value >= habit.target`, `in-progress` для
сохранённого количества ниже цели (включая явный ноль) и `no-data` для отсутствующего результата.
Только процент ограничивается 100%; фактическое количество не обрезается.

Duration-запись хранит целое `minutes` от 0 до 1440. `0` — явный результат,
отсутствие записи — `null` в представлении (без оценки). Строка времени, emoji
и rating не сохраняются в `HabitEntry`. Изменение времени заменяет дневной итог.

`DurationRatingRange` содержит `id`, `label`, `emoji`, `minMinutes`, `maxMinutes`.
Границы включены; последний `maxMinutes: null` означает открытый конец. Сервис
проверяет покрытие с нуля без пропусков/пересечений, уникальность ID и целые границы.
Конфигурация находится в каждой duration-привычке, первоначальные диапазоны —
в `db/duration-defaults.ts`. Текущие границы документированы в README/ROADMAP.
Замена конфигурации пересчитывает оценки в сегодняшнем и историческом представлениях,
сохраняя фактические минуты. Экран «Настройки» позволяет менять границы,
подписи и emoji существующих диапазонов.

## IndexedDB

Имя БД: `zadachnik`, версия Dexie: `4` (нативная версия IndexedDB — `40`).

| Таблица | Первичный ключ | Дополнительные индексы |
| --- | --- | --- |
| `habits` | `id` | `type`, `order` |
| `habitEntries` | `[habitId+date]` | `habitId`, `date`, `type` |
| `tasks` | `id` | `date`, `status`, `goalId` |
| `goals` | `id` | `status`, `deadline` |
| `goalMilestones` | `id` | `goalId`, `[goalId+order]` |

Составной первичный ключ обеспечивает одну запись на привычку и день. Сервис
в одной read/write-транзакции проверяет существование, тип и архивность привычки,
затем выполняет `put`. Повторная отметка заменяет результат, сохраняя `createdAt`.

Для amount-трекера чтение текущего значения, прибавление и `put` выполняются
в одной read/write-транзакции. Одновременные добавления из разных вкладок
не теряются. Принимаются положительные целые безопасные числа; сумма также
проверяется на точность. Запись с несовместимым типом или некорректным значением
не перезаписывается. Для Этапа 2 модели и схема версии 1 уже поддерживали воду;
тогда миграция не требовалась.

Миграция v1 → v2 добавляет отсутствующие `ratingRanges` существующим duration-привычкам
`gaming` и `social-media`. Таблицы/индексы сохраняются. Имена, временные метки,
архивность и вся история не меняются; удалённые seed-привычки не восстанавливаются,
уже сохранённая конфигурация не заменяется. Новая БД сразу получает диапазоны в seed.

Миграция v2 → v3 создаёт пустой `tasks` store. Старые таблицы, индексы и записи
не переписываются; seed повторно не выполняется. Прямой переход v1 → v3 также
сохраняет миграцию duration. Задачи не хранятся в `HabitEntry` и не дублируются
в отдельном календарном хранилище. `localStorage` не используется.

Миграция v3 → v4 добавляет пустые `goals` и `goalMilestones` и индекс `tasks.goalId`.
Существующие строки задач не переписываются: отсутствующий `goalId` означает
отсутствие связи. Старые таблицы, их значения, заметки и timestamps сохраняются.
Переходы с v1/v2 выполняют прежние миграции перед v4, без повторного seed.

Этап 7 сохраняет схему v4: новых таблиц, индексов и миграции нет. Дополнительные
значения `Task.status` используют существующее поле и индекс. Старые задачи и их
временные метки не переписываются; статистические агрегаты в IndexedDB не сохраняются.

Seed выполняется событием Dexie `populate` в транзакции создания БД:
8 boolean-привычек, вода (цель 2000 мл) и 2 duration-привычки. При обычном
повторном открытии seed не запускается и пользовательские данные не меняются.
Записи `HabitEntry` заранее не создаются.

Отсутствие записи отображается как `no-data`, никогда как `failure`. Явный выбор
«Нет данных» сохраняет запись со статусом `no-data`. Отметки других дней остаются
в БД. Архивирование в «Настройках» использует `archivedAt`, не удаляя историю.

Dexie `liveQuery` обновляет интерфейс при изменении хранилища, включая другие
вкладки. Ошибки открытия, чтения и записи показываются пользователю.

`AmountTracker` отображает рассчитанное сервисом состояние и передаёт действия
в `useDayHabits`. Hook подписывает страницу на результаты выбранного дня,
хранит состояния ввода и сохранения отдельно для каждой привычки и дня.
Ручной ввод проверяет `parseAmountInput` в сервисе; поле очищается только после
успешной записи. Быстрые кнопки прибавляют 200/400 мл к тому же `HabitEntry`.
Цель берётся из `AmountHabit` (для воды в seed — 2000 мл).
В календаре тот же компонент использует режим абсолютного итога: `setHabitAmount`
заменяет количество, включая 0, вместо прибавления. Сервис проверяет целое безопасное
неотрицательное значение; `hasEntry` отличает сохранённый ноль от отсутствия записи.

`DurationTracker` — один компонент для обеих duration-привычек. Hook держит
черновик часов/минут отдельно для каждой привычки и даты. Если черновика нет,
форма выводит сохранённые минуты как часы/минуты; после успешного сохранения
она снова следует данным IndexedDB. Ошибка не очищает введённое время.
Пустое отдельное поле считается нулём, но полностью пустая форма не сохраняется.

## Статистика

Этап 7 расширяет недельный обзор duration из Этапа 3 до общей страницы.
Существующие `duration-statistics-service.ts` и недельные компоненты сохранены;
текущая страница использует расчёты произвольных периодов из `services/statistics/`.

### Периоды и получение данных

`period-utils.ts` формирует включённые локальные календарные границы и массив дней:

- `7d` — сегодня и шесть предыдущих дней;
- `month` — с первого числа текущего месяца по сегодня;
- `previous-month` — полный предыдущий календарный месяц;
- `3m`, `6m`, `year` — скользящие интервалы по сегодня: из сегодняшней даты
  вычитается 3, 6 или 12 календарных месяцев, затем прибавляется один день;
- `custom` — обе выбранные даты включены, конец не позже сегодня, максимум 3660 дней.

Календарная арифметика date-fns учитывает короткие месяцы, високосные годы и DST;
фиксированные интервалы по 24 часа и UTC-день не используются. Параметры
`period`, `from`, `to` хранятся в hash и восстанавливаются после reload.
Некорректная ссылка показывает объяснение и возвращает обзор последних семи дней.
Для интервалов от 15 дней дополнительно строятся недели с понедельника по воскресенье;
первая и последняя недели ограничены выбранным периодом.

`StatisticsService.getStatistics` читает все пять существующих таблиц в одной
read-транзакции: привычки, цели и этапы целиком, записи и задачи — по индексу `date`
в выбранном диапазоне. Для привычек, созданных позже начала периода, один
дополнительный запрос составного индекса `[habitId+date]` получает более ранние
ключи записей без загрузки их значений. Они уточняют начало отслеживания, если
пользователь внёс результат задним числом. Запросов на каждый день или компонент нет.
`calculateStatistics` группирует записи по привычкам и рассчитывает весь dashboard
и недельные показатели в памяти из этого снимка.

### Привычки и время

`getHabitPeriodDates` исключает из числа ожидаемых дней даты до локального дня
создания и после дня архивации; сам день архивации включён. Более ранняя запись
сдвигает начало отслеживания, в том числе когда её дата находится до выбранного
интервала. Фактические записи после архивации также остаются видимыми, но пустые
дни после неё не добавляются. Привычка без дней отслеживания в периоде скрыта;
архивная привычка с историей отображается с пометкой. Записи не изменяются.

`habit-statistics.ts` считает success, failure, no-data, число отметок и серии.
Отсутствующая запись и явный `no-data` не входят в знаменатель:
`successRate = success / (success + failure) * 100`. Без явных оценок процент —
`null`. Общая доля успехов взвешивает все явные отметки одинаково, а не усредняет
проценты привычек. Расчёт серий переиспользует `streak-service.ts`, но ограничен
выбранным периодом; текущая серия должна заканчиваться его последним днём.
Пропуски, failure и no-data прерывают серию.

`amount-statistics.ts` считает сумму, среднее, минимум, максимум, дни с записью,
дни достижения цели и дни ниже неё. Достижение означает `value >= habit.target`;
процент — успешные дни / дни с записью. Среднее использует тот же знаменатель.
Явный ноль участвует в расчётах, пропуск не становится нулём или неудачей,
перевыполнение не обрезается. Без записей сумма, среднее, границы и процент — `null`.

`duration-statistics.ts` отдельно для каждой привычки считает фактическую сумму
минут, минимум/максимум, среднее по дням с записью и сумму / календарные дни
отслеживания. Последний показатель описывает распределение записанной суммы;
он не объявляет пропуски записанными нулями. Без записей средние и границы — `null`.
Оценки и число дней каждой категории пересчитываются по текущим `ratingRanges`;
фактические минуты сохраняются независимо от категории. Игры и соцсети не объединяются.

### Задачи и цели

`task-statistics.ts` отбирает задачи по дате дедлайна внутри периода, независимо
от даты создания или выполнения. Исход определяется общим `getTaskOutcome`
на текущий момент, а не восстанавливается на конец исторического периода.
`tasksDue` включает все отобранные задачи. По уточнённой формуле:

- `relevantTasks = completedOnTime + completedLate + failed + overdue`;
- `OnTimeRate = completedOnTime / relevantTasks * 100`;
- `DeviationRate = (completedLate + failed + overdue) / relevantTasks * 100`.

Отменённые, ожидающие срока и выполненные без известного `completedAt` показаны
отдельно и исключены из коэффициентов. При нулевом знаменателе проценты — `null`.
Позднее выполнение, явное невыполнение и активная просрочка остаются разными
показателями. Недельный OnTimeRate использует те же правила.

`goal-statistics.ts` показывает текущее состояние целей независимо от периода:
active, completed, failed, cancelled, просроченные active и средний прогресс
активных целей с одинаковым весом. Прогресс берётся из `goal-service.ts` и
существующих этапов/ручного значения. Архивные цели исключены из этих показателей,
но их количество указано отдельно. Без активных целей среднее — `null`.
Исторические проценты не восстанавливаются: снимки прогресса в БД не сохранялись.

### Подписка и отображение

`useStatistics` подписывается на снимок через Dexie `liveQuery`, включая изменения
из других вкладок. При смене диапазона данные предыдущего периода не показываются;
ошибка чтения имеет отдельное состояние и повтор загрузки. `useCurrentTime`
обновляет момент сразу после минутных границ, при фокусе и изменении видимости.
Это пересчитывает просрочку без записи в БД; смена локального дня обновляет период.

`StatisticsPage` загружается через React.lazy, поэтому графики не включаются в
начальную загрузку «Сегодня». Общий `StatisticsChart` использует Recharts для
дневных amount/duration и независимых недельных рядов: успехи привычек,
задачи вовремя, дни достижения цели воды, среднее время игр и соцсетей.
Для коротких дневных рядов используются столбцы, для длинных и недельных — линии;
у воды показана целевая линия. Boolean-проценты и исходы задач представлены
полосами с текстовыми значениями. Сводки и таблицы доступны без hover;
tooltip открывается нажатием. Пропуски остаются `null` и разрывают линию.
При отсутствии данных или ResizeObserver график не рисуется, текст остаётся.
Недельные показатели не сводятся в общий непрозрачный score.

## Локальный день

Ключ дня — валидированная строка `yyyy-MM-dd`, построенная date-fns из локальных
компонентов `Date`. UTC-день через `toISOString().slice(0, 10)` не используется.
ISO UTC используется только для временных меток `createdAt` / `updatedAt`.

Следующая полночь вычисляется календарно, а не прибавлением фиксированных 24 часов,
чтобы учитывать переходы летнего времени. Hook обновляет день по таймеру, при
фокусе, изменении видимости вкладки и периодически проверяет смену часового пояса.
Перед сохранением повторно проверяется текущая дата, чтобы устаревшая вкладка
«Сегодня» не записала результат за вчера. Календарь разрешает прошлые даты;
общая `assertEditableDate` запрещает будущие даты в сервисах boolean, amount,
duration и заметок, даже если UI ещё не обновился после смены часового пояса.

## Календарь

`CalendarPage` загружается через React.lazy в существующей hash-навигации.
`lib/calendar.ts` строит от 4 до 6 полных недель с понедельника по воскресенье
через календарные функции date-fns. Дни соседних месяцев отображаются приглушённо
и доступны для выбора. Месяц хранится как первый день; переходы декабря/января
меняют год без переполнения даты 29–31. Названия выводятся в русской локали.

Выбранная дата и видимый месяц находятся в hash-параметрах `date` и `month`,
валидируются существующим `isLocalDate` и восстанавливаются после reload.
«Сегодня» выбирает актуальный локальный день и его месяц. У выбранного дня
`aria-pressed`, у текущего `aria-current="date"`; все даты — настоящие кнопки.
Поддерживаются Tab/Enter/Space и стрелки для перемещения между днями.

`CalendarService.getMonth` выполняет одну транзакцию чтения: получает привычки
и записи видимого диапазона через индекс `habitEntries.date` и
`getEntriesForDateRange(startDate, endDate)` с включёнными границами.
Отдельных IndexedDB-запросов на каждую ячейку нет. `liveQuery` пересчитывает
индикаторы после записи, в том числе из другой вкладки. Цвета и агрегаты не хранятся.

Индикаторы означают «Нет данных», «Часть отмечена» и «Всё отмечено», а не оценку
успешности дня. В расчёте участвуют активные boolean/amount/duration-привычки.
Boolean `no-data` и отсутствие записи не считаются заполненными или неудачей;
явные amount/duration нули считаются результатами. История архивных привычек
остаётся в БД и выдаётся методом диапазона, но не входит в сводку активных привычек.

Выбранный прошлый/текущий день использует общие трекеры и сервисы с «Сегодня».
Черновики и ошибки привязаны к дате; смена даты создаёт отдельную форму.
Будущая дата показывает сообщение без редакторов. Обновление истории сразу
попадает в недельную статистику. Ошибка первоначального чтения календаря
показывает единую кнопку повторной загрузки до открытия редакторов.

Заметка — необязательное поле `HabitEntry.note` длиной до 2000 символов.
Добавляется только к существующему результату, без фиктивного нуля; пустой текст
удаляет заметку. Транзакционные изменения результата сохраняют заметку и `createdAt`.
Индексы и версия IndexedDB не изменены: новые поля не требуют миграции схемы.

Серии рассчитываются только для boolean-привычек по всей истории до выбранного
дня включительно. Текущая серия заканчивается строго выбранным днём; лучшая —
максимальная цепочка календарных success. Пропуск, failure и `no-data` прерывают
цепочку, но пропуски не становятся неудачами. Success rate = success / (success +
failure), без `no-data`; при отсутствии оценок показывается «Нет данных».
На экране эти определения указаны явно; агрегаты вычисляются, а не сохраняются.

## Задачи

`Task` содержит `id` (UUID), `title`, `description`, `date`, `time`, `priority`,
`status`, `createdAt`, `updatedAt`, `completedAt`. Описание — строка (по умолчанию
пустая), время — `HH:mm` или `null`. Приоритет — `low` / `medium` / `high`.
Статусы — `active` / `completed` / `failed` / `cancelled`; два последних добавлены
в Этап 7 по уточнению пользователя. Временные метки — ISO timestamp;
календарная дата — существующий `LocalDate`.

Сервис разрешает прошлые, текущие и будущие даты, проверяя их через `isLocalDate`.
Ограничение привычек `assertEditableDate` к задачам не применяется. Время проверяется
как 00:00–23:59. `getTaskDeadline` интерпретирует дату и время в текущем локальном
часовом поясе: указанное время означает точный момент `HH:mm:00.000`, отсутствие
времени — конец дня `23:59:59.999`. Активная задача просрочена строго после этого
момента. `getTaskOutcome` сравнивает `completedAt` с тем же дедлайном: выполнение
ровно в срок своевременно. Исходы `planned`, `overdue`, `completed_on_time`,
`completed_late` и `completed_unknown` вычисляются и не сохраняются; отсутствие
или некорректность `completedAt` не заменяется выдуманной датой выполнения.
`useCurrentTime` обновляет группы и подписи после минутной границы и при возврате
во вкладку; `useLocalDate` сохраняет назначение даты в формах и дневных экранах.

Название обрезается по краям, обязательно и ограничено 200 символами; описание —
5000 символами, с сохранением внутренних переводов строк. UI и сервис используют
один валидатор. Поля ошибок связаны с полями ввода; неверные данные не записываются.

`TaskService` предоставляет создание, обновление, удаление, чтение по ID,
всех задач, даты и диапазона с включёнными границами, выполнение, возврат выполненной
задачи в active, явное закрытие как failed и отмену.
Редактирование и изменение статуса читают актуальную запись и изменяют её в одной
транзакции: ID и `createdAt` сохраняются, изменения статуса не теряются при
параллельном редактировании, удалённая задача не восстанавливается устаревшей формой.
Выполнение записывает `completedAt`; возврат очищает его до `null`. Повторное
назначение уже установленного статуса не меняет timestamps. `failed` и `cancelled`
— конечные состояния: смена статуса из них запрещена в сервисе и недоступна в UI.
Закрыть так можно только active; выполненную задачу сначала нужно вернуть в active.
Закрытие сохраняет название, описание, дедлайн, приоритет и связь с целью,
очищает `completedAt` и обновляет `updatedAt`. Редактирование обычных полей и
удаление задачи доступны и после закрытия; они не меняют её конечный статус.

Активные задачи сортируются по дате, времени (задачи со временем раньше задач
без него), приоритету high → medium → low, `createdAt`, затем ID. Выполненные —
по `completedAt` от новых к старым, затем ID. Внутри failed/cancelled порядок —
по `updatedAt` от новых к старым, затем ID. Группы и сортировка не хранятся в БД.

`useTasks` подписывается через Dexie `liveQuery` только на задачи. Полная страница
читает `tasks`, а дневные блоки используют индекс `date`; API диапазона также
индексирован. Чтение привычек при каждом изменении задачи не требуется.
Изменения появляются без reload, в том числе в другой вкладке этого origin.
Ошибка чтения/сохранения отображается в интерфейсе, доступен повтор чтения.

`TasksPage` открывается через существующую hash-навигацию и React.lazy. Она группирует
задачи на просроченные, сегодняшние, предстоящие, выполненные, не выполненные и
отменённые. Создание/редактирование используют один диалог; удаление и закрытие
как failed/cancelled требуют отдельного компактного подтверждения. Диалог закрытия
объясняет конечность статуса и его влияние на коэффициенты статистики.
Диалоги поддерживают клавиатуру, Escape и восстановление фокуса; длинные формы
прокручиваются в пределах доступной высоты экрана. После отмены фокус возвращается
к открывшей диалог кнопке; после сохранения или удаления — к «Добавить задачу»,
которая остаётся на странице при перемещении карточек между группами.

«Сегодня» использует `DayTaskPanel` с активными задачами текущего дня: название,
время, текст приоритета, выполнение и ссылка «Все задачи». В календаре этот же
блок читает задачи выбранной даты, показывает количество и статусы, включая
будущие дни. Редактирование задач остаётся в полном разделе «Задачи»; правило
будущих дней для редакторов привычек не изменено.

## Цели

`Goal` — отдельная сущность долгосрочного результата, а не разновидность Task.
Она хранит UUID, название, описание, необязательный локальный `deadline`,
`status` (`active` / `completed` / `failed` / `cancelled`), `progressMode`
(`auto` / `manual`), `manualProgress`, `archived` и временные метки.
Просроченность вычисляется для активной цели с дедлайном раньше локального дня;
срок без времени не переводится в UTC. Архив не удаляет цель или её данные.

`GoalMilestone` хранит UUID, `goalId`, название, порядок и timestamps.
Discriminated union разделяет `boolean` с флагом `completed` и `amount`
с фактическим `current >= 0` и `target > 0`. Числовой этап выполнен при
`current >= target`; перевыполнение остаётся в данных. Порядок назначается
при добавлении и сохраняется при редактировании, без drag-and-drop.

В AUTO процент цели — среднее по её этапам с одинаковым весом:
boolean даёт 0 или 100%, amount — `min(current / target, 1) * 100`.
Без этапов результат 0%. В MANUAL используется число от 0 до 100.
Автоматический процент не сохраняется в IndexedDB. Округление выполняется
только для отображения. Статус цели изменяется явно и не переписывает факты:
завершённая цель может иметь прогресс меньше 100%, а 100% не завершает её автоматически.
Связанные задачи не участвуют в проценте, чтобы не считать работу дважды.

Необязательный `Task.goalId` связывает задачу максимум с одной целью.
Привязка проверяет существование цели и задачи в транзакции; для переноса
задачи сначала нужно снять прежнюю связь. Отвязка сохраняет задачу.
Удаление цели в одной транзакции удаляет её этапы и очищает `goalId` связанных
задач, сохраняя их содержимое и статус. Обычное редактирование Task читает
актуальную запись и сохраняет связь. Копии Task внутри целей не создаются.

`GoalsPage` загружается через React.lazy. Подробности адресуются hash-ссылкой
`#goals?id=…`, задача — `#tasks?task=…`; выбранная задача получает фокус и обводку.
Списки, подробности и связанные задачи обновляются через Dexie `liveQuery`.
Общие модальные формы используют `useDialog`: удерживают Tab внутри окна,
обрабатывают Escape и возвращают фокус к доступной кнопке. Ошибки сохранения
оставляют введённые данные в форме.

## Настройки и backup

`HabitSettingsService` читает определения по порядку и меняет имя/описание,
amount target или duration ratingRanges. Type, unit, ID, order и createdAt
не принимаются как редактируемые поля. В read/write-транзакции читается свежий
Habit: сохранение формы не отменяет конкурентное архивирование, а удалённая
при восстановлении другой копии привычка не создаётся заново. HabitEntry
в операциях настроек не участвуют. Валидация есть и в форме, и в сервисе.

Дневная цель — положительное безопасное целое число. Duration ranges используют
существующие включённые границы с нуля, без пропусков/пересечений и с последним
`maxMinutes: null`. Формы меняют существующие категории; диапазоны валидируются
общим `validateRatingRanges` и ограничениями настроек. Для зарезервированного
типа rating не вводится новая система оценок.
Поддерживаемые импортированные конфигурации остаются редактируемыми независимо
от числа категорий, длины их ID и границ выше суток; фактическое время по-прежнему
ограничено 0–1440 минутами. Длинные подписи переносятся в трекерах и статистике.

Историческая модель сохраняется: **текущие target/ranges применяются ко всем
датам**. Изменение настройки может изменить успешность воды/категорию времени,
но не фактическое value/minutes. Это явно написано в UI и README. Snapshot target
или версии конфигурации не вводятся: частичное хранение только новых значений
создало бы разные правила для старых и новых записей и потребовало бы изменения
всех исторических расчётов. Схема Dexie остаётся v4, миграции нет.

Архивирование атомарно выставляет `archivedAt` и updatedAt; восстановление
возвращает `archivedAt: null`. Повторное назначение того же состояния — no-op.
Today уже читает только active; статистика читает всю историю. Calendar DayInsights
использует существующий запрос результатов/заметок с `includeArchived: true`;
архивные строки показаны отдельно для чтения, без лишнего запроса на каждый Habit.
Редакторы записей по-прежнему отклоняют archived Habit. Интервалы архива после
восстановления не сохраняются; агрегаты после восстановления трактуют привычку
как активную. Permanent delete и отдельная очистка базы не добавлены.

`models/backup.ts` задаёт независимую константу `BACKUP_FORMAT_VERSION = 1`.
Snapshot содержит `app`, `formatVersion`, `exportedAt` и `data` с пятью массивами:
habits, habitEntries, tasks, goals, goalMilestones. Это полная пользовательская
БД: определения Habit включают настройки, а Task.goalId и GoalMilestone.goalId —
связи. Отдельной таблицы preferences нет; hash навигации не является пользовательской БД.

Export читает таблицы в одной read-транзакции. Runtime validator создаёт
проверенную копию данных, сохраняя значения, ID, timestamps и отсутствие optional
полей (например, goalId старых задач). Он проверяет структуру всех discriminated
unions, обязательные поля, конечные числа, целые значения там, где это требуется,
локальные даты, ISO timestamps с часовым поясом, rating ranges, уникальность
первичных ключей, соответствие типа HabitEntry и ссылки HabitEntry/Task/Milestone.
Порядок JSON свойств не учитывается. Незнакомая версия не угадывается; лишние
поля версии 1 отклоняются вместо их молчаливого удаления.

UI ограничивает выбранный файл 50 МиБ до чтения, затем вызывает parseBackupJson
и показывает preview. Сам выбор файла ничего не записывает. Перед финальным
подтверждением предлагается скачать текущий snapshot. Import означает **replace**,
без merge: сервис повторно проверяет вход и отделяет его от объекта вызывающей
стороны до первой асинхронной операции. В одной read/write-транзакции всех пяти
таблиц выполняются clear и bulkAdd. Ошибка записи пробрасывается наружу и
откатывает и очистку, и уже добавленные строки. DeleteDatabase/populate не вызываются.

После успеха Dexie liveQuery обновляет подписки, включая другие вкладки.
UI показывает сообщение об успешном восстановлении. При ошибке остаются
preview и возможность повторить; отмена подтверждения не меняет БД. Скачивание
использует Blob и anchor download, импорт — стандартный file input; Chromium-only
File System Access API не используется. Личные данные не отправляются на сервер.

## Границы этапа

Интерфейс использует мобильную базу CSS, затем `min-width` для больших экранов.
Viewport учитывает iOS safe-area; элементы управления рассчитаны на касания.
Целевой браузер iPhone — Safari 16.4+ (минимум Tailwind CSS 4), JavaScript сборки
также нацелен на Safari 16.4. Наличие IndexedDB проверяется до открытия БД;
ошибка доступа обрабатывается тем же экраном повторной загрузки.
WebKit с профилем iPhone входит в E2E-проверки. Проверка на физическом устройстве
остаётся отдельной ручной проверкой, эмуляция её не подменяет.

Каталог `dist` автоматически публикуется на Vercel по HTTPS из ветки `main`.
Текущая hash-навигация работает на статическом хостинге.

Статистика, настройки и backup используют существующие локальные данные.
PWA, Service Worker, backend и синхронизация не реализованы; Этап 9 не начат.
Категории задач, повторения, подзадачи, проекты, теги, drag-and-drop, уведомления,
совместная работа и зависимости задач не входят в текущую реализацию.
